## 2. LCH / TIBORなど他インデックスへの対応

現状はJSCC TONA(円OIS)のみ対応。「次フェーズ」として明示的に保留。
対応する場合、`curve.py`の`bootstrap_curve()`と`swap_pricer.py`の
インデックス生成部分(`ql.Tonar()`固定)を、インデックス種別を引数に

ドロップダウン)も選択肢を増やす必要がある。


## 4. pricingシートのUDF呼び出し回数の集約(会社PCで計測してから判断)

カーブの共有でPython側の計算は1セル数msになったが、Excel上では1セル約170ms
(xlwingsの往復コスト、ARMの個人PCで計測)かかり、再計算時間はUDFのセル数で決まる。
さらに速くするなら、行ごとの4〜5個のUDF(Q・U・V・W・F列)を表全体で1回の呼び出しに
まとめる(結果の列を1か所にまとめるため、pricingシートの列配置の変更を伴う)。
ユーザーの判断: 会社PCでの体感を見てから相談する。

## 7. HistChartの再計算コスト(重く感じたら相談)

HistChartは最新日をRealTimeのライブのレートで計算するためRealTimeを参照しており
(2026-10-04)、RealTimeの値が変わるとF9で全系列が再計算される。2026-10-11に1回の計算
そのものを速くした(3脚×465日の`HistoricalRates`が約3〜4秒→約0.8〜1.1秒、結果は完全一致):
カーブ復元の日付をC++の配列(`ql.DateVector`)から切り出して渡す、TONA実績を差分だけ登録する、
パーレートだけならスワップを1本だけ組む(`swap_pricer.par_rate`)。いろいろなコンベンションの
チャートを見るため、同じ系列の再計算だけが速くなる案は優先しない(ユーザー判断)。
- 残る案(未着手): 昨日までの系列と今日の1行を別のUDF呼び出しに分ける(RealTimeが変わっても
  昨日までは再計算されない)。結果をプロセス内に覚えておく案は、会社PCのメモリに余裕がない
  ため採らない(ユーザー判断、2026-10-11)。
- パーレートをDBに保存する案はユーザー判断で不要(ブートストラップを省けていれば十分、2026-10-04)。
